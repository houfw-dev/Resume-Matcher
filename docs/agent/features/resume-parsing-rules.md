# 简历解析规则（PDF / DOC / DOCX → 结构化 JSON）

本文说明上传的简历如何变成 `processed_data`，以及沿途应用的每一条规则。PDF 与 Word 的差异只存在于**文本抽取**阶段；从 Markdown 转写开始，两种来源走的是完全相同的流水线，因此同一份简历分别存成 PDF 或 DOCX 上传，结构化结果应当一致（仅可能因两种抽取器对表格/换行的转写不同而有差异）。

代码位置：`apps/backend/app/services/parser.py`（文本抽取 + 确定性后处理）、`apps/backend/app/prompts/templates.py`（`PARSE_RESUME_PROMPT`）、`apps/backend/app/schemas/models.py`（`ResumeData` Pydantic 模型）；上传编排在 `apps/backend/app/routers/resumes.py`。

## 流水线总览

```
上传文件（≤ 4 MB，PDF/DOC/DOCX）
  ① 类型/大小 + 真实容器结构校验（有界流解码）
  ② 文本抽取：markitdown（PDF/DOCX）· 字形丢失回退 pypdfium2（嵌入子集字体 PDF）
        · 本地转换器（.doc）· OCR（无文本层 PDF）
        → original_markdown（原文转写，永久保存）
  ③ LLM 结构化（PARSE_RESUME_PROMPT → JSON，抽取引擎人设）
  ④ 19 道 LLM 之后的确定性后处理（无网络，任何模型输出都要修）
  ⑤ ResumeData 校验 + sectionMeta 规范化
        → processed_data（查看页、PDF 导出、诊断、裁缝共用）
```

`original_markdown` 在调用 LLM 之前就写入数据库（状态 `processing` → `ready` / `failed`）；此后构建器保存会用 JSON 覆盖 `content`，但永远不动 `original_markdown`。它还被三处复用：诊断时作为主观项的事实依据、AI 裁缝后恢复精确日期、重试解析时无需重新上传。

## 1. 上传与文本抽取（唯一与文件格式相关的阶段）

| 规则                                          | 内容                                                                                                                                                                                                       |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 支持类型                                      | `application/pdf`、`application/msword`（.doc）、DOCX 的 OOXML 类型；文件扩展名必须与声明的 MIME 一致；上限 **4 MB**。                                                                                     |
| 容器校验                                      | 三类文件分别做真实结构校验（拒绝伪装文件）。PDF 流使用自研**有界** Flate/LZW/CCITT 解码器。                                                                                                                |
| 资源上限                                      | 解压后总量最大 **16 MB**、抽出文本最大 **2 MB**（超限返回 `413`）；转换时限 **120 秒**（超时 `504`）；并发受限量器控制，工作线程在请求取消后仍可安全收尾。                                                 |
| PDF / DOCX                                    | 统一用 **markitdown**（PDF 后端 pdfminer.six）转成 Markdown 文本（表格转为文本，不保留原始二进制排版）。**PDF 嵌入子集字体回退**：部分 PDF 使用嵌入子集字体，markitdown 会把汉字抽成康熙部首/CJK 部首补充块字符（`⼯`/`⻓`/`⻅`…，U+2E80–U+2FDF）且整段数字字形丢失。抽出文本命中字形丢失签名（≥4 个连续空格、`  . -  .` 形日期空壳、或 ≥10 个部首字符）时，自动用 **pypdfium2** 重新抽取；仅当回退文本 CJK 字数 ≥ 损坏文本的 60% 且数字严格更多时才替换，防止 pdfium 重排侧边栏内容误伤正常 PDF。pypdfium2 是纯 wheel 核心依赖（无系统库），与 OCR extra 中的同版本包共用。 |
| 汉字部首归一化                                | 抽取文本在字形丢失回退判定**之后**统一做 CJK 兼容字符归一化：康熙部首块经 NFKC 折叠，折叠结果为繁体或无映射的常用字（`⼾→户`、`⾒→见`、`⾙→贝`、`⾭→青`…）与 CJK 部首补充块（`⻓→长`、`⻔→门`、`⻋→车`…）走静态简体映射表；**不对整段文本做 NFKC**，以免全角标点变半角（`：→:`）破坏中文正则。旧版 .doc 转换结果同样处理。 |
| 旧版 .doc（先嗅探真实容器）                  | `.doc` 扩展名不可信——WPS/Word/Google Docs「另存为 .doc」常产出 OOXML/RTF/HTML 内容。`_sniff_legacy_doc_format` 读文件头分流：**OLE2**（`D0CF11E0…`）→ 本机转换器（macOS `textutil`，其他平台 LibreOffice `soffice`）；**OOXML**（`PK\x03\x04`，实为改名 DOCX）→ 临时文件改后缀，走完整 DOCX 容器校验 + markitdown；**RTF**（`{\rtf`）/ **HTML**（`<!doctype`/`<html`，容忍 UTF-8 BOM 与空白前缀）→ 本机转换器，结果同样过 CJK 部首归一化；**未知头** → `DocumentValidationError`（422）。转换器均未安装或转换超时 → `422`，提示另存为 PDF/DOCX。 |
| OLE2 非扇区对齐尾部（WPS）                   | OLE2 容器校验只接受结构指针（FAT/目录/DIFAT）自洽的复合文档，但**不要求**文件总长度是扇区（512/4096 字节）的整数倍：WPS 保存时会在最后一个扇区后追加非 CFB 尾部（实测 84,121 字节 = 164 个整扇区 + 153 字节签名/水印元数据）。所有指针检查按向下取整的扇区基座计算，尾部部分扇区被忽略，与 `textutil`/LibreOffice 的容忍行为一致；截断到不足三个扇区的文件仍被拒绝。 |
| 无文本层 PDF（扫描件 / 字体全部转曲的导出件） | markitdown 抽出为空时，若安装了可选 `ocr` extra（`pypdfium2` + `rapidocr-onnxruntime`，完全离线）：只识别**前 10 页、200 DPI**。未装 extra、OCR 失败或识别为空 → `422`（提示文件可能是图片版，请先 OCR）。 |
| 空文本                                        | 抽取结果为空白一律不进 LLM，上传失败返回 `422`。                                                                                                                                                           |

## 2. LLM 结构化规则

系统人设固定为「JSON 抽取引擎」。提示词要求只做忠实搬运：照抄措辞，绝不改写、总结、润色、调序、补连接词，也不发明原文没有的公司、技术名词或数字。

### 2.1 sectionMeta（必填，每个有内容的版块一行）

- 6 个内置版块使用固定 id/key：`personalInfo`、`education`、`summary`、`additional`、`workExperience`、`personalProjects`（`isDefault=true`）。其余全部是自定义版块：id = key = snake_case（`isDefault=false`）。
- `displayName` 按原语言**逐字照抄**源标题（「兴趣爱好」「自我评价」「个人总结」「Publications」），不翻译、不自创；`order` 按原文顺序从 0 开始；所有输出的行均可见。
- 校验阶段的 `canonicalize_section_meta()` 随后会把内置版块标题替换为规范英文标题（界面按 UI 语言本地化显示）、隐藏空白的可选版块（不删内容）、按学历分支重写 `order`。自定义版块名永不重命名。

### 2.3 `descriptionStyles`——每条描述行一个样式

适用于工作、项目、自定义 itemList 的每一行：

- **`bullet`**——由渲染器负责自动编号的职责/成果点，适用于三处：项目中的**项目职责/项目亮点**各条目、个人优势（`summary`）下的各条目、工作经历中的职责行。元素文本中绝不带原文编号。
- **`label`**——粗体子模块标题独占一行（项目背景：/ 技术栈：/ 项目职责：/ 项目亮点：…），绝不与下一行合并，也不占用编号；其下的条目从 1 重新编号。**嵌套小标题例外**（渲染层）：项目条目的职责/亮点模块内部，非已知子模块名的短冒号标题（如「重大生产环境问题解决：」「性能调优：」「cpu飙升问题：」，源 PDF 中本是 `1.`/`2.`/`3.` 编号的加粗条目）渲染为模块列表的**一级加粗编号点**（1./2./3. 连续；标题正则三处镜像放宽，允许标题内部出现空格/连字符，故模型改写的 `CPU 飙升问题：` 也能识别）；**其下所有明细行一律渲染为二级复合编号** `1.1、1.2 …`（每个一级点下重新计数、多缩进一个编号槽），不区分存储样式是 plain 还是 bullet——「项目经验存在下级模块、其下内容仍分层展示时用有序列表」的渲染规则在展示层统一编号，存储样式保持诚实不改写。**裸分组标题（无冒号）形态**：源 PDF 职责/成果模块中还常见不带冒号、不带编号的裸加粗分组名（如「架构演进与技术债务治理」「主导促销中心组件设计」，各辖数条成果点），弱模型可能存成普通 `plain` 行甚至 `bullet` 行导致分组被压平。该规则**对所有项目通用**（不针对特定简历），第 9 道状态机用「形状 + 结构」两层规划器 `_plan_nested_group_heads`（三处镜像，见该节）在存储/读时自愈中把合格行提升为 `label`，随后走同一套一级加粗编号点 + 二级复合编号渲染（`1. 架构演进与技术债务治理` / `1.1 …` / `1.2 …` / `2. 主导促销中心组件设计` / `2.1 …`）。
- **`plain`**——无编号、无粗体的正文行：独立段落，以及 schema 无对应字段的自由表格/键值结构。项目中背景类、技术栈类标签下的所有内容行强制 plain，永不编号。技术栈的**存储形态分两种**：① 结构化分类栈（`后端：Java、Spring Boot`、`数据库：MySQL、Redis`，短分类前缀 + 冒号 + 冒号后有内容）每个分类行独占一个 plain 行（builder 仍逐条编辑），渲染为**有序列表**（每个分类行一条编号 `1. 后端：…`，类别内技术名维持「、」内联；混合形态中的裸名行也一并编号）；② 无分类前缀的扁平技术名栈，新解析由第 13 道 `repair_project_tech_stack_rows` 合并为**一个 plain 行**（顿号「、」连接；独立 URL 行同时提升到项目 `website`/`github` 字段），存量分行数据在**渲染层**仍由 inline 合并兜底显示为一段内联自动换行（含中文用「、」、纯 ASCII 用 `, ` 连接）。项目背景等散文体仍逐行成段。
- **成效/效果类标签是平级模块，绝不是亮点的嵌套头**：项目成效/工作成效/实施成效/建设成效/应用成效/业务成效/落地成效/实际成效/量化成效/运营成效/项目效果/实施效果/应用效果/落地效果/运行效果/实际效果这 16 个成效/效果类标签名已纳入三处镜像的已知子标签词表（`parser._SUB_LABEL_CANDIDATES`、`resume_docx._SUB_LABEL_CANDIDATES`、前端 `list-format.ts` 的 `SUB_LABEL_CANDIDATES`，注释互指保持同步）。因此即使它们出现在「项目亮点」模块之后，渲染层的嵌套头判定（`nestedNumberedHead` / `nested_numbered_head`，要求「非已知子标签」）也不会命中——它们走独立模块标签分支：粗体标签行独占一行、后续内容打开**新的列表块且编号从 1 重新开始**，plain 散文行保持无编号，绝不会变成亮点列表里的加粗 `N.` 嵌套头及其 `N.M` 二级点（真实案例 de8ce72b：源 PDF 中技术栈/项目背景/我的职责/项目亮点/项目成效本就是同级标题，修复前项目成效被误编号为 `4.`、其散文为 `4.1`）。这 16 个词**刻意不进 `PROJECT_SUB_LABEL_CANONICAL` 重命名表**（也不进前端同名映射），名称逐字保留——「项目成效」永远不会被归并改写成「项目亮点」；解析侧还会把粘连行（`项目成效：错报率下降约 70%。`）经 `_INLINE_SUB_LABEL_RE` 拆成独立 label 行 + 内容行。这类大模块四（项目背景/技术栈/项目职责/项目亮点）之外的平级模块，其内容行的缩进适用统一的 flush 左对齐规则（见第 5 节「平级模块散文 flush 对齐」）。

**项目子标签四类规范重命名（仅项目适用；工作条目标签逐字保留）**：职责类 工作职责/主要职责/负责内容/核心工作/工作内容/**个人职责/项目责任** → **项目职责**；组合标签 **项目职责与成果/项目职责和成果/项目职责及成果/工作职责与成果/工作职责和成果/工作职责及成果/个人职责与成果/核心职责与成果/职责与成果/职责和成果/职责及成果** 同样归入项目职责（职责 + 成果合并标题打开的是职责编号区，微调可选）；成果/难点类 项目成果/**个人成果**/技术亮点/技术难点/难点与解决/技术难点及亮点 → **项目亮点**；介绍/背景类 项目概述/业务背景/项目简介/需求背景/项目概况/项目介绍 → **项目背景**；技术类 技术选型/技术架构/所用技术/技术清单/技术列表 → **技术栈**。其他标签（项目描述/系统架构…）逐字保留。每个子标签下的条目在渲染时从 1 重新编号，模型不得自行编号。无尾冒号的光核标签（如裸「个人职责」「项目成果」）即使被弱模型标成 `plain`/`bullet`，只要整行精确等于已知别名也会重命名并提升为 `label`，是否带冒号保持原样（不补冒号）；仅整行精确匹配才触发，句中包含别名文字的内容行不动。**成效/效果类 16 个标签（项目成效/项目效果/工作成效…，完整清单见上一条）刻意不在重命名表内**：它们是与项目亮点平级的独立模块，逐字保留原名，不做任何归并改写。

### 2.4 通用格式规则

- **原文一行 = 一个数组元素**。绝不许用逗号、分号或连接词把多行并成一条，也不许把一行拆成自造的多条。**唯一例外**：源简历本身把多个要点写成一个大段（自我评价段落、项目职责长句），模型应直接按 `；`/`。` 子句逐点输出；模型漏拆时由第 16 道后处理 `split_blob_text_sections` 兜底。
- **绝不照抄原文的编号/项目符号**（`1、` `1.` `1)` `(1)` `①` `一、` `•` `- `）到元素文本中——编号由渲染器统一生成。
- `text` 块内每行一个点、以 `\n` 连接，保持原顺序。自定义版块必须原样复刻源格式：保留原标签、标点、换行；不重排、不重绕、不重编号、不重构；表格单元格/键值块每个转成一行 `plain`，绝不用「 - 」拼接。
- **日期一律规范形**：提示词要求输出 `yyyy.MM`、区间 `yyyy.MM~yyyy.MM`、在职 `yyyy.MM~至今`（连接符全篇统一为无空格 `~`，禁止口语化时间描述）；源无月份时才允许年精度 `2020~2021`，**绝不编造月份**。模型未遵守也无妨——第 4 道 `normalize_date_periods` 会把中文年月日、斜杠/连字符/波浪区间、**英文月份名**（`Jan 2020 - Dec 2023`）与所有开放端标记（Present/Current/Now/Ongoing/现在/目前）确定性改写为数字月 + `至今`；尾部括号注（`（实习）`）保留，无法解析的口语化值原样不动。重叠的并行任职保留为独立条目，不合并。
- **句尾标点与空白全篇统一**：列表点（`bullet` 行与所有渲染型字符串数组、summary/自我评价文本行）剥除行尾句读（`。.；;！？!?`），`plain` 散文行保留自己的句号，任何情况下都**不新增**标点；区块内部禁止空白行（空描述行与对应 `descriptionStyles` 按索引等长双删，text 块折叠空行），行首尾修剪、行内连续空白（Tab/NBSP/全角空格）折叠为单空格。提示词约束 + 第 18 道 `normalize_text_hygiene` 确定性兜底。
- **技术英文名词使用规范大小写并全篇统一**（Java、JavaScript、TypeScript、Python、Spring Boot、MySQL、Kubernetes、CI/CD…），禁止输出 `java`/`JAVA`/`spring boot` 这类随意大小写；提示词给规范示例，第 17 道 `canonicalize_tech_terms` 用精选术语词典（最长优先、字母数字边界）做确定性兜底。允许在忠实搬运前提下修正明显的 OCR/抽取损伤（乱码残字、明确的中英文错别字、明显英文拼写错误），但不得改写措辞、润色风格或改动技术事实/数字；意图不确定时照抄源文件。
- 缺失值约定：文本缺省 `""`、数组缺省 `[]`、可选字段 null。源文件中没有内容的版块一律不得输出。

## 3. LLM 之后的 19 道确定性后处理

在 `parse_resume_to_json` 内按以下顺序执行；每一道都是不依赖模型自觉的修复：

1. **`normalize_cjk_compat_deep`**——最先执行，递归遍历整个 JSON（dict 的值改、键不改），把 LLM 照抄部首字符产生的 `⼯`/`⻓`/`⻅` 等归一化为正常简体汉字，否则后续标题、子标签、日期正则全部失配。映射表与抽取阶段的文本归一化共用（见第 1 节）。
2. **`strip_markdown_formatting`**——移除泄漏进结构化字段的 Markdown 强调标记（`**粗体**`、`__x__`、`*斜体*`、`` `代码` ``、`~~删除~~`）：成对标记解包保留文字，孤立 `**`/`__`/`~~`（含跨字段断裂的半边）直接删除；单 `*`/`_` 有边界保护（`A*`、`5*8`、`my_var` 不动）。剥离后对渲染型字符串列表（专业技能/证书/奖项/语言、自定义 stringList 的 `strings`）做去重——标记清理会让仅格式不同的重复行（`英语四级` 与 `英语四级**`）坍缩成同一文本。索引对齐数组（`description` / `descriptionStyles`）不参与去重。
3. **`restore_dates_from_markdown`**——用原文中的日期区间修补被 LLM 丢掉精度或留空的日期。按年份键匹配，并用公司/岗位/学校等身份词在源行及其上下文中打分消歧；匹配有歧义（同年份多段经历）时宁可不改。覆盖工作、教育、项目及自定义 itemList：
   - **英文月份**（`Jan 2020 - Dec 2023`）：修补仅年份的日期；
   - **数字日期**（`2020.06`、`2020年6月`、`2020-06`，含 `-`/`–`/`—`/`~`/`～` 区间与 `至今/现在/目前/Present/Current/Now/Ongoing`）：同样识别并修补为 `YYYY.MM`（连接符随后由第 4 道统一为无空格 `~`，开放端统一为 `至今`）。负向断言保证 `JDK 21.0.1`、小数不被误判为日期；
   - **空 `years` 字段**：当教育/工作条目的时间为空时，只有日期所在行逐字出现该条目的身份词（学校/公司名，阈值 20 分）才填充——项目条目绝不允许偷取工作/教育时间段；
   - 年-only 的目标值（`2025`）可被 `2025 - current` 形态的源日期填充。
4. **`normalize_date_periods`**——日期呈现规范化（用户规则「时间格式全篇统一为 yyyy.MM，在职 yyyy.MM~至今，禁止口语化时间描述」）。遍历工作/教育/项目与自定义 itemList 条目的 `years`，逐字段调用 `canonicalize_date_period`：日期点（数字年月日、斜杠/连字符、**英文月份名**、纯年份）解析后零填充为 `yyyy.MM`，两点输出 `p1~p2`、开放端（七种 `至今/现在/目前/Present/Current/Now/Ongoing` 标记）输出 `p1~至今`、单点输出 `p1`；所有连接符（`- – — ~ ～`）与任意空格统一为无空格 `~`；年-only 不编造月份（`2020~至今` 合法）。保守闸门：token 之外只允许连接符/空白，尾部可有一个括号注（`（实习）`）；无法解析的口语化值（`三年经验`）、多标记/多点怪值**原样返回**；规范形输入幂等字节不变。`personalInfo.workYears` 不是日期，不动。`restore_dates_from_markdown` 内的 `_canonical_numeric_date` 也已改为 `~` 连接，improve 链同源产出规范形。
5. **`backfill_personal_info_from_markdown`**——只扫描文首头部区域（前 2000 字符，从第一个 `标签：值` 到下一个版块标题为止）；标签必须起始于一个排版边界（空白/竖线/冒号），因此求职意向里的「电话销售」不会被当成电话。name/phone/email/title/location 仅在为空时回填；性别/年龄/工作年限/学历**以原文为准覆盖**（修复「统招本科(211)」被剥成「本科」）；邮箱/电话用实体正则提取；语言能力切分后以并集合入 `additional.languages`。头部标签表同时识别个人链接格（`博客地址/个人网站/个人主页/个人博客/个人网址/主页/博客/网站/网址/Website/Homepage/Blog`、`领英/LinkedIn`、`GitHub`，标签内允许 markitdown 插空）：识别到链接标签即**截断前一个事实的值跨度**，并把 Markdown 链接 `[文本](URL)` 折叠为 URL 目标后，按联系方式语义仅在 `website/linkedin/github` 为空时回填。四个事实字段（性别/年龄/工作年限/学历）的值先经 `sanitize_header_fact_value` 清洗：值内出现内联 Markdown 链接、裸 URL（`http(s)://`/`www.`）或**空白分隔后的嵌入式 `标签：` 边界**（标签内允许空格，如 `学 校：`）时，从粘连边界起截断，干净前缀逐字保留——真实案例：`工作年限：13年 博客地址：[fengba.blog.csdn.net](https://…)` 此前因「博客地址」不在标签表而把整段链接并进 workYears 并反盖 LLM 的正确值，现 workYears 得 `13年`、website 得 `https://fengba.blog.csdn.net/`；`本科 学 校： 西安电子科技大学` → `本科`。无冒号/链接的合法值（`5年大型医院项目，3年电商`）字节级不动。
6. **`sort_timeline_sections_newest_first`**——工作经历、教育经历按**起始日期倒序**（识别 `2018.05`、`2020年5月`、`Jun 2020`、纯年份）。无法解析日期的条目沉底并保持原相对顺序；项目与自定义版块不动。
7. **`extract_project_header_fields`**——把描述中的「项目规模：…/团队规模：…」行提升到 `scale`，把「项目角色：…/担任角色：…」行提升到 `role`；仅填充空字段（绝不覆盖），并把该行从描述中删除。
8. **`normalize_item_sub_labels`**——把只有标签的行（「工作职责：」）强制为 `label` 样式；把标签与内容粘连的一行（「技术架构：Spring AI …」）拆成粗体标签行 + 内容行（项目背景/技术栈内容强制 `plain`）；并执行项目专用的四类规范重命名。重命名/提升覆盖三种弱模型形态：带冒号独立行（任意样式）、`label` 样式的无冒号光核行、以及被错标成 `plain`/`bullet` 的无冒号光核别名行（整行精确匹配才触发，尾冒号有无保持原样），使第 9 道区域状态机能正确识别四个子模块边界。
9. **`repair_project_label_regions`**——项目描述区域的样式状态机（只处理 `personalProjects`，工作经历不动），修复弱模型把子标签区域内的行标错样式：
   - **背景/技术栈区**（项目背景/项目描述/技术栈/系统架构/架构说明，以及别名标题）：区域内所有内容行强制 `plain`——技术栈下每个技术名在存储中独占无编号正文行，绝不以大号粗体标题渲染；展示/PDF/DOCX 时由渲染层把技术栈 body 合并为一行内联（见第 5 节），项目背景等散文体保持逐行堆叠；
   - **职责/亮点区**（项目职责/项目亮点）：区域内内容行强制 `bullet`；被错标成 `label` 的整句散文（以粗体前缀开头但携带完整句子的行）降级为编号点；**裸分组标题提升（对所有项目通用的结构规则，非样本特判）**——规划器 `_plan_nested_group_heads` 在每个职责/亮点模块 span 内分两层判定：① **形状层** `_is_nested_head_shaped`：字符串行、无点号标记、无尾冒号、≤16 字、无 `，。；！？、,.!?;：:` 句读/枚举标点，样式 `plain`/`label`/`bullet` 均可（弱模型常把头存成普通 bullet）；② **结构层**：合格头必须满足「下一同 span 内容行为**明细形**（不满足头形状：长句/带标点/带编号等）」「上一同 span 内容行不是头形（两个相邻短行是并列点而非头+头）」且「同一 span 内合格头 **≥2 个**（分组结构必有多组；孤立短行是普通条目）」。合格头在样式循环前一次性规划为索引集合，统一提升为 `label` 交给渲染层输出 1./1.1/1.2 两级编号。三处镜像：`parser._is_nested_head_shaped`/`_plan_nested_group_heads`（按 `heading_kinds` 划 span）、`resume_docx._is_nested_head_shaped`/`_plan_nested_group_heads`（按标签判定划 span，仅 `canonicalize_labels` 项目位点）、前端 `looksLikeNestedGroupHead`（形状层）/`planNestedGroupHeads`（结构层）。全库 16 份简历实证：真分组项目（如邹利平两个项目共 9 个头，含全 bullet 存储形态）全部命中，扁平 `负责…` 同级列表（叶宏汉）、夹在长句间的孤立短点（张向科）、相邻短行对（01-Java/宋杰波）零误伤；规划在原始存储样式与读时自愈后数据上结果一致（幂等）。护栏：带源编号的枚举行（`1）…`/`2）…`，点号标记正则命中）、超长或含标点的散文行、无后继明细的收尾行、单头模块一律不提升；
   - 已知四类以外的短独立标题（`难点/方案/效果：` 等 `_STANDALONE_SUB_LABEL_RE` 命中项）保持 `label` 但关闭已知区域，其后的行不被强制改样式；没有任何 plain/bullet 区域标题的项目整项不动。重跑第 8 道的行规范化时使用 `split_descriptive_only`：只物理拆分背景/技术栈粘连行，职责/亮点粘连行保持单行（沿用历史渲染语义）。**渲染层**把职责/亮点模块内部的这类未知标题还原为源 PDF 的编号加粗条目（见第 5 节「嵌套分级有序列表」）：标题行是一级加粗编号点 1./2./3.；其下明细行一律渲染为 1.1/1.2 二级复合编号（不区分存储样式 plain/bullet）。
10. **`extract_education_credentials`**——把弱模型粘进教育 `description`（固定四列行里的「专业」**单**单元格）的奖项/荣誉/证书/资格行迁出：扫描 专业/奖项/获奖/荣誉/奖励/证书/资格/资质/认证（中英双语标签，英文带字母数字边界保护，`Rewards:` 不会误匹配 `Awards:`）+ 冒号的内联标签；专业段剥掉 `专业：` 前缀留在描述里；奖项/证书条目先按句级标点（`；;。`/换行/逗号）切段并剥编号、再按顿号拆分，避免 `2、` 留下裸 `2`；混合标签 `荣誉证书：` 按条目关键词（证书/认证/资格/资质/执照）逐条分流到两个数组；语言标签（`语言：/外语：/语言能力：/外语水平：/英语水平：/Languages:` 等，裸核「语言」带「编程/开发/脚本/程序/设计/计算」固定宽负向后顾，`编程语言：Java` 绝不触发）同样识别，条目按语种/考试关键词路由到 `additional.languages`，区域内出现强证书词（PMP/CPA/证书/License 等）时证书优先；与 LLM 已抽出的重复条目由第 19 道去重坍缩。无标签命中时描述字节级不动、幂等。
11. **`extract_misfiled_credentials`**——第 10 道的 list 版：弱模型把凭证区整块粘进**工作/项目描述**（`description`/`descriptionStyles` 双数组）时确定性归位。识别两种形态：块标签区（`奖项：` 独占一行、其后每条一行，`label`/`bullet`/`plain` 样式都认——工作描述在归一化链中不跑子标签样式修复，不能只认 `label`；无冒号光核标签仍要求 `style=="label"`）与行首粘连行（`奖项：国家奖学金、PMP证书。`，含一行多标签），行首锚定 + `(?<![A-Za-z0-9一-鿿])` 后瞻防止英文 `Rewards:`⊂`Awards:` 与中文编程语言误触。四重保守闸门：① 行首锚定 + 精确标签核；② **佐证闸门**——区域/粘连段内每条都必须命中间标桶关键词（奖项：奖/荣誉/奖学金/Dean's List…；证书：PMP/CPA/证书/License…；语言：英语/雅思/CET/N1…），任一条无佐证则整区域/整行保留；③ **区域行数帽 6**（块标签后超过 6 行未遇边界则放弃整个区域，标签行也保留，从其后继续扫描）；④ 遇未知标签行（`工作职责：` 等 `_STANDALONE_SUB_LABEL_RE` 或任意 label 样式行）/非字符串行即区域边界。路由 `_route_credential_item`：强证书词最强优先，其次按区域类型偏好奖项/语言，无佐证条目随区域默认桶。块区域一行=一条目（不按标点切分，防止职责句碎成假证书），仅粘连行走第 10 道同款标点切分。删除时双数组按索引集合严格等长重建（掏空为 `[]`，样式不错位）；`additional` 懒创建；异常时整条目原样保留。幂等，重复条目交第 19 道坍缩。无标签散文（「持有 PMP 证书的轮岗」「获校二等奖学金」孤行）绝不搬运，留给微调长尾兜底。
12. **`strip_source_point_numbering`**——再次剥离所有已存数组元素中的残留编号/项目符号（工作/项目描述、专业技能、证书、奖项、语言、自定义 strings 与 items）；散文类字段不动。
13. **`repair_project_tech_stack_rows`**——项目技术栈区域的结构修复（只处理 `personalProjects`，工作经历不动），在第 9 道区域样式修复与第 12 道编号剥离之后运行，针对弱模型两种实测误形态（真实案例：Forest 简历把源文件一行 `技术栈：Java、Kotlin、…、HttpClient` 拆成每个技术名一个 plain 行，并把独立成行的项目地址 `https://forest.dtflyx.com` 吞成技术栈第 7 行；同简历 5 个项目的 `website`/`github` 字段全空）：
    - **独立 URL 行提升**：技术栈区域内**整行只有一个链接**的行（裸 `http(s)://`/`www.` URL，或整行单个 Markdown 链接 `[文本](URL)` 折叠为 URL 目标，尾部句读自动剥除）按 host 路由——`github.com` 及其子域入空的 `github` 字段，其余入空的 `website` 字段；只填空、绝不覆盖模型已抽值或本道已填字段（扫描期即时占位，同一字段的第二个 URL 不会在应用填充时反超首个胜者），无法路由的 URL 逐字留在正文（不丢信息）；
    - **扁平技术名栈合并**：剩余技术名行（无分类前缀）合并为**一个 `plain` 行**，分隔符统一用中文顿号「、」——技术栈标签是中文语境，即便技术名全为 ASCII（`Java、Kotlin、Spring Boot`）也按中文排版（用户明确规则）；合并同时移除了会命中渲染层 inline 降级正则（`^前缀{0,9}：`）的 `https:` 行，修复整栈被错误逐行堆叠的问题；
    - **结构化分类栈不合并**：区域内任一行命中分类行判定（短分类前缀 + 冒号 + 冒号后有内容，如 `后端：Java 17、Spring Boot`；正则与 `resume_docx._TECH_STACK_CATEGORY_RE`、前端 `TECH_STACK_CATEGORY_RE` 三处镜像）时保持逐行，因为渲染层按分类行输出每条一个编号的有序列表，合并会摧毁该结构。**独立 URL 行显式豁免分类判定**：`https://…` 的前缀 `https` + 冒号恰好满足短分类形状，不豁免会把含未路由 URL 的扁平栈误判为分类栈而拒绝合并（三处镜像谓词均带同一护栏：parser 用 `_extract_standalone_url_row` 识别，DOCX/前端用 `http(s)://`/`www.` scheme 前缀判定——Markdown 链接与 `www.` 行本就不命中分类正则，裸 URL 是唯一误判源）；
    - 区域边界为下一个标签行（已知子标签或任意 `label` 样式行）；区域内全是 URL 的退化形态整段逐字保留（不让「技术栈：」标签孤悬）；已是单行的栈 no-op，整体幂等。**本道不进入读时自愈链与 DOCX 构建器**（保持存量分行数据的 builder 逐行编辑契约与微调区域索引不变），存量简历需要新形态时点「重试解析」重跑管线即可。
14. **`reconcile_custom_section_shapes`**——修复自定义版块「声明类型与内容容器错装」：弱模型给了 `sectionType` 却把内容写进另一个容器（真实案例：`stringList` 的「其它」版块两条 GitHub/博客链接被写进 `items` 而 `strings=null`，所有模板只按 `strings` 渲染，于是只显示标题、内容不可见，诊断 #1 报「有标题无内容」）。两种错装确定性迁移而非丢内容：① `stringList` 无 `strings` 但 `items` 有带标题条目 → 由各 item 的 `title`（剥源点号标记、丢空条）生成 `strings` 并清空 `items`；② `itemList` 无 `items` 但 `strings` 非空 → 按 `{"id": n, "title": value}` 合成条目（与 Pydantic 的字符串→item 强制同构）并清空 `strings`。声明容器本身已有内容时不动，故对已修复数据重跑为 no-op（幂等）。读时自愈链与 DOCX 构建器镜像同一道（见第 5 节），存量简历无需重新导入。
15. **`promote_work_departments`**——当 `department` 为空且描述**第一行**样式为 `plain`、形态符合严格的独立组织单元特征（短句；无句读标点；以 部/事业部/事业群/中心/组/室/科/处/分院/大区/条线/团队 或 Department/Dept./Division/Team/Group 结尾）时，将其移入 `department` 并从描述中删除。bullet 样式行、完整句子、版本号字符串绝不提升。
16. **`split_blob_text_sections`**——弱模型把多个要点合并成一个大段时的拆点兜底，产出的多点文本以 `\n` 连接，渲染器自动显示为**有序列表**：
    - **自我评价类 `text` 块**：仅限 `customSections` 的 self-evaluation 族键（`self_evaluation`/`self_eval`/`self_appraisal`/`selfassessment`，自我评价/个人评价/个人总结等标题均解析入此槽）且 `sectionType=="text"`；其他自定义文本块（兴趣爱好等）不动。
    - **项目「项目职责」区**：以含「职责」的 `label` 行做区域状态机，只拆区域内的 `bullet`/`plain` 字符串行，拆出的每个子句继承原行样式（保持与 `descriptionStyles` 一一对齐）；项目背景/技术栈/项目亮点区不拆；没有任何 `label` 行的项目无法安全定位职责区，整项不动。
    - 分隔符仅为中文 `；`/`。` 与半角 `;`——**绝不按 ASCII `.` 拆**（保护 `JDK 21.0.1`、`2020.09`、小数）；拆出的子句去掉分隔标点，并逐段剥离残留原文编号；只有一个子句的行（含已逐点换行的文本）字节级保持不变，末尾句号也保留。工作经历描述不参与此工序。
17. **`canonicalize_tech_terms`**——技术英文术语大小写确定性规范（用户规则「技术英文名词全篇大小写统一」；`app/services/tech_terms.py`）。精选约 80 个术语（Java、JavaScript、TypeScript、Spring Boot、MyBatis-Plus、MySQL、Elasticsearch、Kubernetes、CI/CD、Vue.js、Node.js…）编译为单条大小写不敏感正则：最长优先拼接（`javascript` 不会被 `Java` 抢先替换），边界 `(?<![A-Za-z0-9])…(?![A-Za-z0-9])` 允许邻接 CJK/标点（`mysql集群→MySQL集群`）但阻止 `Vue.jsx`、版本号内部误匹配。作用于 summary、工作/项目条目的 title/department/description、additional 四数组、customSections 全部内容字段；**跳过** years、personalInfo（姓名/电话/邮箱/链接）、company/institution、sectionMeta 与 URL。深拷贝不 mutate 入参，幂等。必须排在卫生/去重之前：仅大小写不同的重复行（`java`/`Java`）规范化后由第 19 道坍缩为一条。
18. **`normalize_text_hygiene`**——呈现卫生（用户规则「连接符、空格、缩进与符号用法全篇统一；句尾标点统一不能混用；区块内部禁止多余空行、不允许连续两行及以上空白行」）。逐行 `strip` + 折叠行内连续水平空白（Tab/NBSP/全角空格 → 单空格）；描述空行与其 `descriptionStyles` **按索引等长双删**（位置过滤会让后续 bullet/plain 错位到邻居），text 块（summary 与自定义 text）逐行 trim 并丢弃空行（区块内零空白行），渲染型字符串数组丢空条，头部字符串字段仅外层 trim。头部 trim 后对四个事实字段重放第 5 道的 `sanitize_header_fact_value`、对三个链接字段重放 `normalize_header_link_value`——读时自愈链（`normalize_resume_data`）与 DOCX 构建器都经过本道，故修复上线前解析的存量简历（如 workYears 粘着 `博客地址：[…](…)`、educationLevel 粘着下一表格格 `学 校：…`、website 存着 Markdown 链接原文）无需重新解析，刷新即愈合，且幂等。**句尾标点**：bullet 行 + 专业技能/证书/奖项/语言/stringList 等列表点 + summary/self-evaluation 文本行剥尾标点 `。.；;！？!?`（仅尾部连续序列，保守）；plain 散文行与非自我评价 text 块保留原句号，**绝不补标点**。排在结构性拆分/修复之后（新生行也被清洗）、去重之前（卫生后变得相同的行由第 19 道坍缩）。
19. **`dedupe_resume_lists`**——编号剥离与第 10/11 道的奖项/证书/语言迁移、第 14 道的容器迁移、第 17 道大小写统一、第 18 道标点/空白清洗都可能制造重复行（`1、英语四级` 与 `英语四级`；`java` 与 `Java`；`MySQL。` 与 `MySQL`），最后对渲染型字符串列表统一去重一次。

## 4. Schema 校验

- `description` 被强制为字符串数组；`descriptionStyles` 与描述行**一一对齐**：多出的截掉、缺失补 `bullet`、非法值归为 `bullet`（见 `schemas/models.py`）。
- 整体通过 `ResumeData` 校验，随后规范化 `sectionMeta`（内置标题归位、**补齐 LLM 漏发但数据非空的内置版块行**、隐藏空白可选版块、按学历分支排序）。没有实质内容的结果判为失败。
- LLM 调用带 JSON 合法性校验与重试；解析失败的简历标记为 `failed`，「重试解析」用已保存的 `original_markdown` 重跑，无需重新上传。

## 5. 渲染侧镜像修复（老数据无需重新解析）

前端在渲染时重复执行后端识别逻辑，使规则上线前解析的简历也能正确显示；后端读取侧（GET 简历时的 `normalize_resume_data`、DOCX 构建器）也会对存量数据重放同样的修复。清洗链为 `normalize_cjk_compat_deep → normalize_date_periods → repair_project_label_regions → extract_education_credentials → extract_misfiled_credentials → reconcile_custom_section_shapes → canonicalize_tech_terms → normalize_text_hygiene → dedupe_resume_lists(strip_markdown_emphasis_deep(...)) → canonicalize_section_meta`，DOCX 在深拷贝上执行同一链并随后再跑 `promote_work_departments`；智能微调的候选 overlay 只跑其中**样式保持**的子集（术语规范 + 卫生，见 [fine-tune.md](fine-tune.md)），完整链会撤销用户显式要求的 plain↔bullet 排版翻转。前端镜像同序：`lib/utils/date-period.ts` → `tech-terms.ts` → `text-hygiene.ts`，在保存归一化器与 `<Resume>` 包装器展示 memo 各执行一次。**两个例外**：

- 第 16 道 `split_blob_text_sections` 只在导入解析时执行，渲染侧/DOCX 不做镜像拆分——大段拆点依赖源文本的子标签上下文，存量简历若需有序列表需重新解析。第 13 道 `repair_project_tech_stack_rows`（技术栈分行合并 + 独立 URL 提升到 website/github）同为解析专用、不做读时镜像：存量分行数据仍由渲染层内联合并显示，需要落库为新形态时用「重试解析」重跑管线。
- 第 3 道 `restore_dates_from_markdown` 的**数字日期/空时间取证填充不镜像**：它从 `original_markdown` 取证，而字形丢失型 PDF 的已存原文中数字本身已丢失，「重试解析」复用的也是这份损坏原文。此类存量简历只有**重新上传 PDF**（新上传走文件字节的 pypdfium2 回退）才能补回教育/工作时间。注意：第 4 道 `normalize_date_periods`（不依赖取证，只规范化已存在的日期串）在读时/DOCX/前端**照常镜像**，故存量简历的英文月份、连字符、`Present` 等呈现刷新即变为规范形。

## 7. AI 接地层的双证据源（`extra_evidence`）

解析产物不仅供渲染，也是所有 AI 改写（improve / enrichment / fine-tune）的事实底座。`app/services/resume_preservation.py` 的 `finalize_ai_resume` / `validate_confirmed_resume` / `grounding_review_warnings` 向后兼容地新增 `extra_evidence: str | None = None`：

- 不传或传 `None`（improve、enrichment 等既有调用方）时，接地仍只看结构化 source，数字剥离、相似度闸门、review 警告的算法与逐字节行为不变，既有测试零改动。
- **智能微调**（见 [fine-tune.md](fine-tune.md)）传入 `original_markdown` 作为第二证据源：候选行中的数字若出现在原文证据中则不计为虚构；定性行相似度在 `source_tokens ∪ evidence_tokens` 上计算；原文中有、结构化漏掉的职责/成果允许补回。证据中仍无据的数字照剥，无法证实的定性表述以 `GROUNDING_REVIEW` 警告保留交人工核对。范围裁剪（`restrict_to_scope`）与冻结规则（`personalInfo` / `sectionMeta`）在接地之后再强制执行。

## 8. 规则制品（声明式数据外置）

解析器的词表、别名映射、正则字符串与数值阈值不再硬编码在 `parser.py` 里，而是以带校验的版本化制品发布；19 道后处理的顺序、区域状态机、日期消歧打分、容器校验、`ResumeData` schema 与 CJK 字形表是结构契约，仍留在 Python。

### 8.1 制品链路

```
rules/parser_rules.yaml          人工编辑源（阈值/词表/正则字符串）
rules/shared_terms.yaml          跨端共享词表（canonical_tech_terms 等）
        │  uv run --with pyyaml python -I scripts/export_parser_rules.py
        ▼
app/services/parser_rules.json   随包入库的运行时唯一制品（只读 JSON）
        │  app/services/parser_rules.py（Pydantic 校验 + lru_cache，导入期 fail-fast）
        ▼
parser.py / resume_docx.py / tech_terms.py   经 typed 访问器绑定
```

- PyYAML 只是**导出期临时依赖**（`uv run --with`），运行时与 pytest 不引入新依赖；生产代码只读 JSON。制品分四段：`spec_version`、`thresholds`（11 个标量，bool 被显式拒绝）、`vocabularies`（15 个：有序词表或别名映射；`header_field_labels` 的叶子是正则片段，导出期与加载期各编译一次）、`patterns`（32 个 `{pattern, flags?}`，flag 白名单仅 IGNORECASE/MULTILINE/DOTALL/UNICODE）。
- 加载器 `get_parser_rules()` 与 `config_cache` 一样假设单 worker、进程级缓存、无运行时热更；坏正则/缺段/未知键/空白或重复词条都在加载期响亮报错。访问器按形状区分：`vocabulary_list()` / `vocabulary_mapping()` / `pattern()` / `int_threshold()` / `float_threshold()`，类型不符抛 `ValueError`。
- **动态组合正则仍是代码**：`_HEADER_LABEL_RE`、`_INLINE_SUB_LABEL_RE`、`_CANON_EN_POINT_RE`、`_START_DATE_RE`、教育段标签、错放凭证行、`_EMBEDDED_LABEL_RE` / `_STANDALONE_SUB_LABEL_RE`（量词 `{0,n}` 由阈值驱动，pattern 形状留代码）——外置的是叶子片段与量词阈值，组合算法不可配置。安全预算常量（4MB/16MB/2MB、OCR 页上限、递归深度 10 等运维参数）不进规则包。
- `resume_docx.py` 过去手工镜像 parser 的词表/正则/阈值，现统一经同一加载器绑定（`_STANDALONE_LABEL_RE` 刻意少一个源序号前缀可选组——调用方已先剥离点号标记，这一形状差异由测试锁定）。

### 8.2 前端代码生成与 drift 门

技术名词规范大小写表（77 条 `canonical_tech_terms`）有后端与前端两个消费方：

```
rules/shared_terms.yaml
   ├─ export_parser_rules.py → parser_rules.json → tech_terms.py（tuple 绑定）
   └─ generate_frontend_rules.py → apps/frontend/lib/generated/tech-terms.generated.ts
                                   （入库的生成产物，文件头 DO NOT EDIT）
```

前端构建不依赖 uv/PyYAML，所以生成产物随代码入库；`lib/utils/tech-terms.ts` 只保留 ES2017 无 lookbehind 的捕获组等价实现与字段覆盖逻辑，词表从 generated 模块 re-export。`scripts/check_generated_rules.py`（纯标准库）比对 generated TS 与后端 JSON 制品，drift 时退出码 1 并给出再生成命令，已挂入 `.githooks/pre-push`（第 3 门，与 locale parity 同列，无需 Node）。**保密边界**：生成器只导出公开词表；诊断 criterion/qc 与主流栈组等价口径永不离开服务端。

### 8.3 解析提示词可覆盖

`PARSE_RESUME_PROMPT` 默认模板仍在 `app/prompts/templates.py`（36 条内容锁测试不变），但允许在 `config.json` 用 `parse_resume_prompt` 覆盖：经 `PUT /api/v1/config/feature-prompts` 保存，保存期校验必须含 `{schema}` 与 `{resume_text}` 两个占位符（缺失返回 422 结构化 detail；空串表示回退默认）。运行时 `parser._resolve_parse_prompt()` 取自定义或默认模板；自定义模板 `.format()` 失败（如带外编辑留下未转义 JSON 花括号）时服务端记 WARNING 并回退内置默认，客户端维持通用报错面。自定义提示词中的字面 JSON 花括号必须双写 `{{ }}`。设置页「Content Generation」区块提供编辑文本域，七语种文案同构。

### 8.4 改动规则后的固定动作

1. 编辑 `rules/parser_rules.yaml` 或 `rules/shared_terms.yaml`；
2. 仓库根目录跑 `uv run --with pyyaml python -I scripts/export_parser_rules.py`，涉及共享词表再跑 `uv run --with pyyaml python -I scripts/generate_frontend_rules.py`；
3. `git diff` 两个制品确认变更仅来自预期 YAML 编辑；
4. `cd apps/backend && uv run pytest`（golden 测试 `tests/unit/test_rule_artifacts.py`、`test_tech_terms.py`、`test_generated_rules_drift.py` 会在默认值漂移或手工改 generated 文件时变红），前端 `npm run test && npm run lint && npm run typecheck`。
